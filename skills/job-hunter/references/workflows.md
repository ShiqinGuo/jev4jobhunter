# 按意图执行

所有模式遵守 SKILL.md 的授权、浏览器与外发边界。只加载本轮需要的章节和平台参考，命令包装不另建流程。

## setup：初始化或更新

1. 确定数据目录与已有资料，运行 store.py init；遇旧 state 则按 profile-schema.md 迁移。重复执行只补缺项，不覆盖用户的事实、策略或历史。
2. 从用户提供的简历 / 文本抽取 profile.md，标注材料来源和未知项。优先使用当前请求与已有资料，不重复询问能推断的字段。
3. 补充真正缺少的目标方向、地点 / 工作方式、硬条件。默认先搜索与起草，用户要求自动发送时再记录动作范围。将授权与求职偏好分开，不能拿默认设置当用户授权。
4. 保存 policy.json；保留已有明确约束和用户更正。按需生成 opener 草稿，直接给出可检查结果和使用示例。可选浏览器 recon 不影响本地 setup 完成。

更新在线简历时逐段保存、重新打开核对，工作经历、项目经历、专业技能保持各自职责。日期只用材料或用户明确补充；用户允许项目沿用工作日期时按对应工作映射。删旧项目后核验列表不再出现，不能把输入框已填当成保存完成。招呼语采用用户最终确认的版本；用户说“已经编辑好，就这样”后只核对同步，不继续润色或追加第二条。初次起草保持简短，按用户要求写学历、毕业届别、经历身份和岗位兴趣，毕业届别不能拿当前年份代替。

## search 与 daily：推进一轮

search 只发现与比较；daily 同时处理用户所需的新消息、候选与待办。每轮按以下决策推进，不要求固定搜索次数或固定平台：

1. 读当前条件、状态与未解决事项。涉及本地持久化或外发时先获取运行锁，读取 profile / policy 指纹。本轮 --dry 传播到所有分支，禁止招聘平台外发。
2. 优先只读核对 pending / unknown，避免后续重复执行；确认为成功 / 未提交才 resolve。遇验证码 / 登录验证暂停对应平台，继续其他可完成内容。
3. 按用户指定节奏安排投递与聊天。配置 `policy.search.batchBeforeReply` 时，先连续搜索、筛选和投递，达到该批量才集中读会话并回复，随后继续下一批；不要每投一个就切聊天。没有批量配置时再按用户关注的线程与有时效待办安排。若只要求搜索则跳过聊天阶段。
4. 按当前平台与匹配策略读列表、精读相关 JD，得到推荐 / 排除 / 待确认及原因。用稳定 key 和旧外发状态去重；候选缓存失效时重评。
5. 有已授权的发送范围则在本轮与当日限额内执行；其余保存候选和完整草稿。用户要求按平台实际额度执行时可把对应 dailyLimits 设为 null，不能因默认数字提前结束，也不能为凑数量放宽硬条件或声称更多职位已申请。若用户要求主动按城市 / 关键词搜索，使用真实站内搜索与筛选，保存查询、城市、结果覆盖和续查位置；推荐流不能代替指定的搜索流程。平台明确限额后停止对应动作，次日先核实恢复条件，不通过换入口或换账号绕过。
6. 保存 logs/<日期>-<runId>.md 和候选清单，摘要列已成功、待核对、草稿、跳过原因和下一步；没有匹配时说明搜索覆盖范围。释放锁，按任务归属清理标签与临时正文文件。

一次运行若等用户决定，先完成独立的读取与材料准备；不持锁无限等待。释放锁后收到回复，重新获取锁并刷新页面与状态再执行。

### 批量投递优先

用户可配置 `search.batchBeforeReply`（例如 50）。按本轮批次已确认成功、去重后的新增职位计数；同一岗位的招呼与后续简历分享只算一个，失败、pending、unknown 和浏览过的候选不充数。Boss 新沟通与正式申请仍分别统计，不混称正式投递成功。把批次起点、成功数与搜索游标写入 `state.scheduler`，中断后继续累计，不能重新从零计算。

批量是查看会话的间隔，不是每日上限。达到批量后集中检查、处理来信并记录检查完成时间，再开始下一批，直到平台实际限额。批次未满时，普通半小时检查让位给当前投递批次；已达到平台限额、搜索结果确实耗尽或搜索被阻断而聊天仍可用时，可先处理不足一批的会话。独立回复轮次没有未完成投递批次时按原定时计划执行；日报仍按时汇总。用户明确要求立即处理某会话时按最新指令执行。

## reply：回复具体消息

1. 唯一定位平台、公司、HR、岗位与会话，读取当前问题及必要历史。未读标记可用于发现，稳定 inboundId / turn fingerprint 用于去重；文本或日期相同不意味着同一消息。
2. 先检查 humanTakenOver / needsReview 与已有动作。明确由用户本人发的消息暂停自动接管；存在未落 state 的旧审计或 pending 动作则先核对。
3. 根据 JD + profile + 历史回答实际问题，用对方使用或用户要求的语言。不把所有技术栈塞进短回复，不夸大未证明的技能和成果。
4. 对约面、薪资、到岗、联系方式、附件等先检查已有具体授权。信息不够就准备草稿并在 alerts 更新待答点；不先自动发一句过渡话术。
5. 若用户已明确让 Agent 发给这位 HR，且内容和权限齐备，按 SKILL.md 的完整外发流程执行。已由用户接管的线程可按本次具体指令使用 oneShotHandover，不要求用户额外执行 resume，也不解除长期自动暂停。常规回复仍经过文本检查与 outbox。网页出现用户新消息或编辑器有未识别文本时先保护现场、刷新上下文。
6. 成功后记录回执与 lastInboundId；失败或未知分别记录，不把“已起草”写成“已回复”。

对相同来信的普通回复和承诺回复是同一对话回复，不能通过改变 kind 重复发送。确需补充第二条时必须有独立的新指令 / 事件标识与相应授权。

## apply：执行选中的申请 / 草稿

“投这几个”按用户指向唯一选中的职位执行，不扩大到整张候选表。目标不明确时先完成能准备的材料，再只问目标定位。

1. 重新打开原始职位，确认仍在招聘、账号正确、旧候选没有硬条件变化。历史成功、待核对记录或用户手动申请标志优先，不能因为本地候选状态还没更新就重投。
2. 整理招呼文本或申请表答案与附件；按平台副作用确定动作。Boss 的 greet 与 ATS 的 application 分开统计。
3. 用户已有具体“使用此简历申请这些岗位”的指令即可覆盖对应上传与提交，不重复要求另一次确认；陌生必填声明、额外承诺或资料版本变化不在原范围内时，给出已准备材料和缺少的决定。
4. 对多步表单，在首次会外传的填写 / 上传前 begin，使用同一 action ID 到最终回执。上传成功不等于申请成功；中途断线按 unknown 留待核对 / 续办，不从头新建申请。
5. 发送前再比对草稿文本、表单、收件人、附件 hash。版本变化时更新本地准备结果并重新核对授权。没有文件上传能力则交付附件、答案和停留位置，明确剩余步骤。
6. 回执确认才 resolve succeeded。结束输出逐项真实结果和证据位置。

## report 与 resume

report 默认只读本地报告，优先呈现待用户处理事项和 unknown / pending。统计打招呼、正式申请、回复、面试阶段；说明最后同步时间。用户要求实时更新时才去浏览器读状态。不反复推送相同警报。

只有招聘方明确发出面试邀请才计为进入面试阶段，并记录来信证据、通知用户。投递、发简历、已读、普通回复或我方询问约面都属于前期沟通；双方确认日期时间才计为面试已确认。

resume 先按用户关键词匹配 threads。唯一目标时清除 humanTakenOver / needsReview 并刷新上下文；无匹配或多匹配则列必要候选让用户确定，不批量交还。恢复的是处理资格，仍遵循现有外发授权。用户要求暂停某会话时设置相应标记；要求暂停全部自动运行时同时按授权暂停相关宿主任务。

## schedule：宿主调度

按 [runtime.md](runtime.md) 使用 run_ledger.py 记录轮次和补报。宿主提示只引用 Skill、data-dir 与当前 policy，不复制城市、黑名单和授权全文。日报生成与交付分别记录；是否触发、是否完成和是否通知均须有各自证据。

只在用户要求定时、重复执行或修改已有计划时使用。日常 daily 不创建、续建或恢复定时任务。

1. 从当前宿主的真实调度工具 / 文档确认支持范围、时区、持久性、需保持打开的会话 / 电脑条件。没有调度能力就给出已准备的任务描述、数据目录、执行窗口与人工运行方式，明确“未创建”；不虚构 CronCreate 等工具。
2. 将用户请求整理成可读的任务描述：使用 job-hunter、准确 data-dir、目标平台、模式（包括 --dry）、配额、授权来源与结果摘要要求。定时本身不新增外发授权，也不把简历全文或密钥放进任务提示。
3. 使用宿主支持的时区表达指定时间；用户没给必要时间则询问。已有计划按真实任务 ID 与数据目录匹配，优先更新；不能因为另一求职方案名字也含 job-hunter 就取消它。
4. 按宿主工具要求创建 / 更新 / 暂停 / 删除，只有成功回执才记录 state.scheduler。修改当前已有任务时保留用户未要求变更的字段；取消后不能在下次 daily 自行重建。
5. 回报实际计划、模式、时区及宿主已确认的运行条件。不沿用旧版本“固定 7 天过期”“终端关着也能跑”等未经本宿主确认的假设。

通知优先宿主任务结果 / 当前对话。Windows notify.ps1 只是插件级可选工具；独立 Skill 不需要它。用户明确配置外推渠道后才发送最少摘要，不转发整份简历或完整聊天；推送失败不影响已提交动作的状态。
