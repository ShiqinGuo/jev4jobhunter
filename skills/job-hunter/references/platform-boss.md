# Boss 直聘网页适配

范围：`https://www.zhipin.com` 的求职者网页。路由与选择器是定位线索；2026-09-07 已用 Kimi WebBridge 实测搜索、滚动加载、沟通回执和简历编辑。仍以当前可见页面为准，不把一次实测的配额或机制当作所有账号的固定规则。

## 导航与读取

| 目标 | 历史入口 / 线索 |
|---|---|
| 职位列表 | `/web/geek/jobs`，也可从首页“职位”进入 |
| 搜索 | 站内搜索框“搜索职位、公司”，城市用可见筛选器选择 |
| 详情 | 从职位卡打开；历史链接形如 `/job_detail/<id>.html` |
| 消息 | `/web/geek/chat`，或顶部“消息”入口 |

先按 [browsing-safety.md](browsing-safety.md) 读取本地限制，再在 Boss 可见筛选器中设置策略可表达的硬条件，读回城市、经验、薪资等已选项确认生效。不能只改 URL 后假定筛选成功。经验、学历、职位类型等只设置用户策略已有的硬条件；只有 policy 明确配置 `search.salaryFilter` 时才把薪资范围作为 Boss 原生筛选，否则仍按软参考处理。

先看平台当前自然加载的职位列表，以稳定 ID 与本地历史去重，再按卡片信息粗筛。明确不符或已联系的卡片不打开详情；当前列表的候选才逐个进入详情。职位可能是左侧列表、右侧详情的布局，也可能从卡片打开独立详情页，两者都按一次一个处理。打开后确认标题、公司、地点与卡片一致，再读全文并完成匹配判断及必要外发回执，才处理下一候选。列表标签不能代替 JD；年限判断按 matching.md 与当前 policy，用户已允许的范围不因本人实际工龄不足再次排除。

搜索结果支持向下滚动继续加载。当前自然加载批次的每张卡片都已排除、暂挂或处理完后，才对实际职位列表滚动一次；等待加载并以真实新增 ID 确认下一批。不要滚动右侧 JD 后误以为加载了列表，也不要预加载多批后统一筛选。不写死平台每次的卡片数量，不修改 pageSize / cursor，不批量打开详情或用多标签并发读取。首屏没有合适项不代表结果耗尽，也不是换城市的理由。没有增长时先观察加载状态与末尾提示，排除访问限制后按普通故障流程有限恢复。记录筛选项、城市、关键词、当前批次去向、已见 ID、末尾卡片和是否到底，便于中断后续查。

登录以当前可见账号、消息入口和登录提示综合判断。单独看到 URL 含 `_security_check` 不足以判定拦截；需结合空白内容、验证码或明确安全提示。

## 立即沟通与申请不是同一动作

- “立即沟通”可能发送平台预设招呼语、创建会话、弹确认层或提示额度。**点击本身视为外发**，事先登记 `greet` 动作；不能为了探测其行为先点击。
- 不要求用户开启自动招呼语，也不改平台设置。优先通过当前可见设置核对已启用文本；不能用旧账号的文案代替。用户已授权本轮原生沟通（包括允许自行选择测试岗位），无需再索要逐条文案授权；看不到平台将发的文本时，只对 Boss 的 greet 使用 `contentMode: "platform-default"`，`content` 为 null 或空字符串，登记后 `content` 与 `observedContent` 均为 null，不能填写“平台默认招呼”等占位消息。该模式不支持普通回复、自定义文本、附件或表单答案。
- 默认招呼提交前保存当前账号上下文、岗位详情和无成功提示的页面基线。单次点击后，同一账号上下文、同一岗位新出现“已向BOSS发送消息”的明确平台回执，可确认本次沟通成功；无需为证明发送而额外点击或强求气泡同时可见。保存前后原始页面证据；未读到实际文本时 `observedContent` 保持 null，不从整页无关文本猜招呼。只进入聊天、按钮变“继续沟通”、错误账号/岗位、缺失提交前基线或旧提示都保留 unknown，不能重发。自定义文本仍按原来的文本匹配规则核验。
- 点击后先读结果。平台已发招呼语时不要再手动补发 opener。只看到聊天页而没有成功证据则记 `unknown`；只有明确确认未发送才走新的受控发送步骤。
- 若弹出发送简历、交换联系方式等内容，按实际副作用重新核对用户授权。一个招呼授权不能自动扩成附件授权。
- 不默认招呼语上限为 300 字；读取当前限制或错误提示，生成满足限制的完整短版，不机械截断。
- 报告区分“已打招呼”“已发简历”和“已完成申请”，不要统称已投递。

## 聊天

1. 用“未读”筛选和页面最后消息发现变化。打开后核对公司、HR、关联职位；列表预览和日期不能独立判定新旧消息。
2. 读取足以覆盖问题的上下文，必要时滚动历史。同一天重复文本也可能是新消息；优先可见的消息 ID，否则组合作者、时间、文本和相邻消息位置生成 turn fingerprint，证据不足则暂挂。
3. 从顶部职位卡 / “查看职位”补充 JD。一个 HR 可能聊多个岗位，不能仅按 HR 姓名选上下文。
4. 用所选通道点击可见会话条目，读取实际打开的会话核对身份；旧版本点击失效的经验不代表当前通道不可用。
5. 只在已有授权及 `pending` 记录后填写编辑器；发送前检查文本和发送按钮可用。历史版本 Enter 会直接发送，不用 Enter 换行。
6. 新增的我方气泡文本、收件人、时间和送达 / 已读状态共同作为回执证据。输入框清空本身不算成功。

## 旧 DOM 提示（只在当前工具允许 DOM 时使用）

| 区域 | 历史选择器 |
|---|---|
| 职位卡 / 标题 | `.job-card-wrap` / `a.job-name` |
| 详情操作 | `.job-detail-op`，`a.op-btn-chat` |

| 顶部职位卡 | `.top-info-content` |
| 消息历史 | `.message-content`；旧 `.chat-content` 实际是推荐联系人区域 |

不要要求这些选择器全部存在才允许读取；新账号无会话、详情尚未选中、页面懒加载都可能正常。

## 标识与失败处理

- 列表不继续加载时先被动核对实际滚动区域、加载状态和新增职位 ID。历史上后台标签可能加载停滞，只作排查线索；优先正常切回已归属标签并观察。任何恢复都须先排除访问限制并经过单步入口，不使用焦点仿真或临时 CDP 绕过该流程。
- “还剩 N 次”是剩余额度提示，不是限额耗尽。读清确认层；确认后仍须看到发送回执才记成功。2026-09-07 某账号实测 150 次达到当日上限，仅作为带日期观察，不写死通用每日上限。
- 详情空白、点击无反应或筛选未更新，先被动观察并区分普通加载失败与访问受限、异常行为、安全验证或“请稍候”等异常等待页。不能因为 HTTP 200 或命令成功就继续。只有普通加载失败才允许有限刷新恢复并重新核对账号、筛选和职位；已经触发提交的动作只核对回执，无法确认则保留 unknown，禁止再次点击补发。

- 职位 key 优先 `boss:<详情链接中的稳定 ID>`。保留原始 URL 供复核，不存 cookie、签名参数或令牌。
- 线程 key 优先当前工具可见的稳定会话标识；拿不到时用公司、HR、职位和线程链接共同生成本地键，并记录 `identityConfidence: low`。不能仅因姓名相同合并；疑似重复先核对再发。
- “今日沟通上限”只记录该平台的 greet 限额。访问受限、异常行为或安全验证则停止证据适用账号上下文的新页面请求和外发，保存提示及恢复条件；已有页面可被动观察。后续心跳先查本地限制，未到恢复时间不刷新、重新登录或换账号试探，到期也需一次正常核验后才能解除。普通登录失效与访问限制分开处理。用户明确指定独立新账号时，按 browsing-safety 的 select-account-context 流程核对并记录账号范围；旧账号限制不能自动扩张为新账号限制。
- 不点击与用户任务无关的收藏、举报、购买配额、设置、简历编辑等按钮。
