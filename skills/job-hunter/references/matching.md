# 职位筛选与解释

## 条件不是关键词计数

从 profile / policy / 本轮用户条件整理必须满足、偏好和排除项。用户指定的专业、行业、岗位类型优先；不要默认所有人都拒绝销售、外包、远程、应届岗位或需要某种学历。

列表用于粗筛，JD 全文用于决定推荐或投递。结合语义处理否定和上下文：“不接受外包”不代表岗位是外包，“培训新人”不等于收费培训。明确收费、押金等可疑要求单列证据与原因；未证实的公司风险不写成事实。

硬条件结果为 `pass / fail / unknown`。只有确凿冲突才判 fail；薪资面议、经验表述含糊、公司规模缺失等归 unknown，说明影响。要求补事实的候选可以留下，不补造信息投递。用户尚未形成筛选策略，或招聘反馈暴露错配时，按 [intake.md](intake.md) 引导；先检查已有规则是否漏执行，不把执行错误归为资料不足。

## 薪资、地点与语言

- 保留薪资原文，再记录 currency、period（月 / 年 / 时）、base 与 bonus、每年薪数、区间、税前税后。只有用户设定硬底线时，范围上限低于底线才是明确冲突；`strict: false` 的期望用于排序，交叠或相近的合适岗位仍可选择，不把软期望变成筛选硬门槛。
- 不直接比较 CNY/月 与 USD/年，不把奖金和股权当作确定现金。只有用户要求换算时查对应汇率并注明日期、计算假设；缺资料就标不可直接比较。
- 地点区分办公室所在地、可远程范围、时区、搬迁要求和工作许可。所谓 remote 不自动等于全球可远程。
- 沿用招聘方 / 用户选定语言，不要求中文占比。技术名词、代码仓库链接等按上下文与授权处理，不因为含英文就拒绝回复。

## 可解释评分

默认用下列维度帮助排序，可根据岗位性质调整权重；分数只是本批候选的辅助排序，不表示录用概率。

| 维度 | 默认分值 | 依据 |
|---|---|---|
| 核心职责与实际经历 | 40 | 用户做过的工作与岗位实际任务 |
| 必需技能 / 资格 | 30 | 材料中的事实和明显缺口 |
| 地点、工作方式、薪资等条件 | 20 | 已知满足项及待确认项 |
| 用户偏好与发展方向 | 10 | 行业、团队、工作内容等偏好 |

用户要求比较时输出推荐级别、匹配证据、缺口 / 未知和下一步；自动投递只保存支持决定的必要依据，不逐岗制作评分报告。分数可选，缺画像或 JD 就不用虚假的精确分数。平台显示的 HR 活跃度只能辅助排序，不代替匹配。

搜索比较的候选表含公司、职位、地点 / 工作方式、薪资原文、匹配理由、待确认事项、来源链接、查看时间。默认展示最相关的 5–10 个；这个展示数量不限制用户已授权的持续投递。

## 何时使用 Jev

见 [SKILL.md](../SKILL.md) 的「何时使用 Jev」。粗筛与详情判断可用 Jev 做类型化判断；本文件的硬条件（pass / fail / unknown）、排除项和发布者类型规则仍由规则先行，Jev 只覆盖规则判不动、需要读懂 JD 语义的部分。Jev 的概率与置信度不改变本节对软硬条件的处理方式。

## 缓存与去重

- 将用户点名排除的公司及明确别名写入 targets.excludedCompanies，按 [runtime.md](runtime.md) 获取生效配置并执行校验；既有会话也查排除条件。自然语言排除项仍需要语义判断，不宣称只用词匹配可以识别所有外包或猎头。

- 发布者类型同样属于用户排除项。`policy.search.excludeHeadhunterPosted: true` 时，页面标注“猎头职位”或发布者明确为猎头 / 猎头顾问的岗位直接跳过，不新沟通、不提交申请、不再发送简历；旧候选和已联系岗位后续索取简历也需重查。记录页面证据与 `headhunter-posted` 原因，保留已有投递与会话历史。身份不明时读取职位和发布者信息，不仅凭公司名推断；此项不默认启用，也不把所有外包岗位等同于猎头发布。

- 先执行用户最新排除项，再判断匹配度。排除项可针对实际用人方或招聘项目，不能因更换猎头、发布公司、城市或职位 ID 就重新投递。实际用人方 / 项目有明确证据时记录 `opportunityGroup` 与证据；不同会话仍保留各自历史，不凭公司名猜测所有岗位属于同一项目。
- 经验按用户明确的投递策略判断，实际工龄仍如实表达。用户已允许尝试某年限范围时，不再以本人正式工龄不足排除该范围，也不额外要求 JD 写“接受应届”；仅有泛泛“宽松”而没有具体范围时，才保留尚未满足的硬门槛待核查。只限在校生、特定毕业届别、明确拒绝当前身份等独立条件仍核对。“优先”技能用于排序，不逐项升级为必需技能。
- 查询只使用 `search.queries`，用户未指定时才根据已确认方向建立候选查询；指定后不能把相关技术词当作自动扩展许可。城市、固定关键词和平台筛选保持用户设定。结果少先按浏览流程继续滚动或核实加载状态，不以低通过率、数量不足或本批完成为由换词、缩减经验项或跨城。

- 已成功沟通 / 申请，以及 `pending / unknown` 外发记录不随候选归档消失；操作前始终查它们。
- `candidate / shortlisted / skipped` 都不是已投。`--dry` 的候选可在下次正式运行执行。
- 对筛选结果记录 `evaluatedAt`、`profileFingerprint`、`policyFingerprint` 和 JD 版本 / 摘要。资料或策略变化、JD 明显更新、超过 `recheckAfterDays`（默认 7）时重新判断，不能因为曾跳过就永远排除。
- 同一公司多人联系可以提示冲突；没有稳定证据不能自动合并会话。不同 HR 对相同问题的合理短回复不应被跨会话去重拦截。
