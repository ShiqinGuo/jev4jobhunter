# 通用招聘网站 / 公司招聘页

用于没有专用适配的站点。它提供可见页面流程，不宣称某个站点已经验证。第一次访问时用 drivers.md 的 recon 建立本轮能力记录；不必先给站点编写一整份适配文档才开始找岗位。

## 发现与匹配

- 从用户提供链接、站内搜索或公开搜索进入；搜索摘要只用于发现候选，打开原始招聘页面再确认仍在招聘、工作地点、薪资口径与要求。
- 从可见标题、公司、岗位 ID、详情链接建立身份。没有岗位 ID 时用完整规范化详情 URL 的哈希；仅移除明确的追踪参数，ATS 的 query 参数可能就是岗位 ID，不可全部剥掉。
- 一个职位同步到多个平台时记录 `sameOpportunityAs` 关联。不能只凭公司与标题相同就合并；明确是同一 requisition 才避免跨平台重复申请。
- 按 matching.md 解释匹配。JD 不完整、职位已关闭或页面要求登录时报告该事实，不从相似岗位补写要求。

## 申请表单

1. 阅读当前职位和申请入口，识别是否跳转外部 ATS、是否登录、需要哪些文件和必填项。
2. 优先先在本地准备答案；有些平台输入即自动保存。只有用户已要求申请或已允许填写时才填网页，`--dry` 不填申请表。
3. 逐字段映射用户资料，记录答案来源。工作许可、签证、搬迁、薪资、到岗、背景声明等缺事实时标为待答，不使用对候选人“更有利”的默认值。
4. 选择对应语言 / 版本的简历，确认文件存在；授权绑定具体附件。没有上传能力则交付材料和手动上传位置，不用别的通道绕过工具限制。
5. 阅读复选框的含义；与申请无关的营销订阅不主动勾选。带声明或承诺的选项需在用户授权范围内。
6. 一个申请用一个 `application` 记录，在首次上传 / 自动保存前登记整份已准备材料，后续步骤沿用该 action ID。中途资料或授权范围改变时先停下核对；不把多步表单算成多次申请。聊天中单独发附件用 `share_resume`。
7. 最终提交前核对岗位、整份答案、附件和授权。完成后保存可见申请编号 / 回执；没有回执则记 `unknown`，先检查申请列表，不重投。

## 消息与跟进

- 网站没有聊天能力就只跟踪申请，不额外转去邮件或社交平台联系 HR。
- 邮件 / 消息能力存在也不自动扩大授权；发到哪个渠道、哪个联系人按用户请求执行。
- 查看跟进状态不等于授权发催促消息。准备跟进建议或在用户已授权的时间和范围内发送。

## 沉淀平台经验

只有反复出现且影响操作的站点特性才值得建立 `platform-<slug>.md`。记录检查日期、来源页面、稳定标识、导航方式、会外发的按钮、成功证据与已知限制；去掉个人信息。日常运行把临时观察记在用户数据目录，不改已安装插件文件。
