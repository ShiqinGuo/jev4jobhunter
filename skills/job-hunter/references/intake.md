# 信息补充与策略引导

用于初始化、改变求职方向、批量投递前仍有关键条件不明，以及招聘反馈显示策略需要调整时。目标是让用户容易回答，并把回答转成实际筛选和沟通行为。

## 先整理，再提问

先读简历、profile、当前 policy 与用户已提供的上下文，分清已知事实、明确偏好、待核实项和 Agent 建议。先检查既有规则是否执行错误；投递超出用户允许的年限范围应修正筛选，不能归咎于用户没有填够信息。用户已明确允许的试投范围不因本人实际工龄不足再次询问或排除。

只选本轮最影响结果的少量缺项提问，说明它会改变什么。用户不清楚如何选择时，用已读的具体岗位帮助比较，例如“这个岗位做业务 API，另一个主要做模型训练；你更想做哪类工作？”不要让用户先交一份完整策略，也不要抛出所有字段让其填写。

没有答案的部分保留未知，继续独立的搜索与草稿。只有依赖该答案的筛选决定、事实回复或承诺等待补充。已明确提供的信息直接使用；不在每次定时运行里重复确认个人资料。

## 按决策选择问题

下表是按需选择的引导，不是每位用户都必须回答的问卷。示例中的选项与条件不作为默认值。

| 决策 | 优先从材料提取 | 必要时怎样问 | 如何影响执行 |
|---|---|---|---|
| 职责方向 | 实际做过的任务、能独立交付的内容 | “同样写 Python，你优先做业务后端、AI 应用，还是数据处理？哪些方向不考虑？” | 定主投与补充方向，按主要职责筛选，不能只匹配技术词 |
| 身份与经验门槛 | 毕业时间、在校/毕业状态；正式工作、实习和项目分别记录 | “这段经历是正式工作还是实习？日期是否准确？” | 判断校招资格和正式工龄；不把实习或个人项目相加冒充正式工龄 |
| 筛选宽严 | 已明确的硬条件、可放宽项 | “职责合适但年限高一档的岗位，你希望只保留明确愿意放宽的，还是也列作尝试候选？” | 分清硬冲突、明确放宽和待核查；试投建议与已授权范围分开 |
| 城市与面试方式 | 目标城市、当前所在地、搬迁意愿分别读取 | “你愿意入职去这些城市；面试阶段能去现场，还是只接受线上？” | 目标城市不等于当前所在地；愿意搬迁不等于能异地线下面试 |
| 薪资取舍 | 期望、最低可接受值及月/年、税前/税后口径 | “这个范围是优先考虑，还是低于下限就不投？奖金是否另算？” | 软期望用于排序，硬底线才排除；不能因低薪回复多就自动降薪 |
| 岗位与渠道排除 | 已排除的公司、项目、发布者或用工形式 | “你排除的是猎头发布，还是外包/派遣这种用工形式？” | 区分发布渠道与实际用工，不从拒绝一家推导为拒绝整个类别 |
| 常用招聘回复 | 当前城市、在职/离职、到岗条件 | “目前在哪个城市、是否在职、拿到 offer 后多久能到岗？” | 保存可复用事实；“offer 后一周”保留触发条件，不改成固定日期或随时到岗 |
| 执行目标与节奏 | 本轮用户要求、已有额度及发送范围 | “本轮优先集中投递还是先推进已有意向？有数量目标时，合适岗位不足怎样收尾？” | 区分数量目标、每日上限、查消息间隔；不能为凑数突破硬条件 |

日期等材料足以判断经历时，不再询问“有几年经验”；身份或经历性质不清楚时才补问。平台“1–3 年”标签不等于接受应届，“在校/应届”也可能只招在校实习生，最终按完整 JD 与明确招聘反馈判断。

批量投递开始前，对仍未知且会反复阻塞普通回复的城市、在职状态和到岗条件，可以合并问一次；这些缺项不阻塞不依赖它们的岗位搜索或已授权沟通。面试具体时间、联系方式等只在当前操作需要时补齐，信息已知仍按既有发送或承诺授权使用。

## 把回答变成可检查的策略

事实与来源、更新时间写入 profile.md；筛选偏好与执行策略按 [profile-schema.md](profile-schema.md) 和 [runtime.md](runtime.md) 写入 policy.json。事实、Agent 建议和用户同意分开记录。现有 schema 未提供机械校验的扩展项，要明确由 Agent 在读取 JD 时执行，不声称脚本已经强制拦截。

给出简短策略摘要：主投什么、哪些是硬排除、哪些仅用于排序、还缺什么及影响。用户已明确决定的直接保存并执行，只问确有取舍的缺项；不再要求整体二次确认。

将已确定策略落实为“平台可设置的筛选 + 完整 JD 复核 + 沟通条件”。例如用户确定初级岗位范围后，设置对应平台年限标签，核查正文是否超出允许范围或只接受在校生；已允许的范围不额外要求应届例外。不要把某次用户选择的年限、城市、薪资或每日数量固化成通用默认值。

用户回答后更新相关待答事项并按授权继续原任务。状态有新变化或招聘问题确实需要更精确信息时再问，不在每轮输出里重复播报已保存资料。

## 反馈复盘

用户要求复盘，或现有聊天反复出现同类门槛冲突时，先用可获得的记录解释哪里失配。数据范围按任务需要选择，不默认每次全量抓取或创建定时复盘。读取范围、时间、缺失资料及历史快照需明确。

- 区分普通回复、对方明确索简历、我方主动分享、面试邀请和确认排期。索简历是兴趣信号，不能证明基本条件已经过筛；未回复不等于拒绝，泛化“不合适”不能强行归因到工龄或技术。
- 岗位画像除正样本外，还要看同类岗位投了多少、等待多久。不要仅因某类索简历数量多就认定效果最好；小样本和城市、日期、渠道差异限制推断。先修正有直接证据的错配。
- 将原因分成已证实的门槛冲突、待用户补充的事实/取舍，以及仍未知。既有硬条件漏执行，直接纠正；降低薪资、扩大城市或改变排除范围属于新的选择，先给具体候选和影响，再问缺少的决定。

用证据引导用户，而非让用户自行诊断：“这些岗位明确要求线下面试，你目前只接受线上，所以没有推进。是否仍保持线上限制？”只在该选择尚需调整时询问；已经明确且未变的限制继续执行。单个 HR 的限制先用于对应岗位，不自动升级为全行业硬过滤。
